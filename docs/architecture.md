# Décision d’architecture — couche agentique autour de Forgejo

**Décision initiale : 21 octobre 2026; mise à jour de preuve : 28 octobre 2026.** Cette décision s’appuie sur les sources épinglées dans [l’inventaire](source-inventory.md), pas sur les affirmations de leurs README seules.

## Options évaluées

| Option | Ce qu’elle apporte | Coût et limites observés | Décision |
|---|---|---|---|
| **Interfaces autour de Forgejo, peu modifié** | Réutilise Git, issues, PR, revues, protections, statuts et API REST. L’agentique peut garder exigences, missions, contexte et preuves dans un noyau séparé. | `head_commit_id` lie la tête candidate, mais l’API publique n’accepte pas de base attendue. Une course source a reproduit la fusion avec `CommitsBehind` périmé. Une contre-mesure jetable dans une deuxième copie source transmet la base attendue jusqu’au push CAS et passe les tests sélectionnés, mais elle n’est pas dans le produit et n’élimine pas les side-effects LFS ni le défaut de requeue AutoMerge. Un verrou local ne coordonne que les écrivains qui le prennent sur le même hôte. | **Choisie pour le pilote sous condition :** faire du service le seul écrivain de merge, tenir le verrou coopératif jusqu’au POST et au read-back, et empêcher les merges de contournement par permissions. Ce protocole est en cours de démonstration; sans contrôle de tous les écrivains, l’API actuelle ne suffit pas. |
| Fork Forgejo limité | Peut lier le SHA de base attendu à la préparation et à l’écriture du merge, et imposer la condition aux clients autorisés. | Une expérience de correction source dans une copie jetable (13 fichiers modifiés, plus un test non suivi) applique un lease Git et couvre les chemins API, Web et AutoMerge ordinaires sur une sélection de tests. Le run groupé est vert avant une dernière assertion du test; cette assertion et le paquet service/pull passent séparément. La suite complète, LFS, réqueue AutoMerge et toutes les variantes serveur ne sont pas démontrées; une correction réelle devrait traiter leur compatibilité et coût upstream. Cela ne rend pas automatiquement le runner sûr. | À évaluer si l’autorité unique ne peut pas être imposée ou si le modèle doit résister à un écrivain Forgejo hors protocole. **Le patch expérimental n’est pas appliqué au produit ni au clone officiel propre.** |
| Fusion profonde GitSpace + Forgejo | Pourrait réunir des concepts de preuve au même niveau de code. | GitSpace est un noyau d’évaluation locale, pas une forge ni un orchestrateur complet; il ne crée pas de PR et ne lie pas la preuve au candidat/base/politique. Licence `UNKNOWN`; pas de runtime partagé identifié. | Rejetée pour le lot. Fusion impossible à justifier fonctionnellement et juridiquement avec les preuves actuelles. |

**Preuve MERGE-011 (23 octobre) :** dans deux répétitions instrumentées sur Forgejo `ea9ae1e174ac290febcd92f57e7a28ccb58262d0`, une PR cible passe `CheckPullMergeable`, une PR concurrente avance le ref Git avant le rafraîchissement DB, puis la cible est fusionnée malgré `block_on_outdated_branch=true`. Le commit final contient le merge concurrent dans son ascendance : l’essai démontre une décision de protection fondée sur un état DB périmé, pas la perte du changement concurrent. Il ne transporte aucune preuve externe et n’établit donc pas une acceptation de preuve obsolète. Ce test rouge est réalisé dans une copie jetable; il ne relie pas ce commit au binaire local v17. L’interface autour de Forgejo demeure la décision pour le pilote local seulement si tous les merges passent par un écrivain coopératif unique. Si un autre écrivain doit rester autorisé, il faut comparer une précondition base côté serveur. Le test, ses SHA et ses readbacks sont décrits dans [MERGE-011](../evidence/merge-011-base-freshness-race-local-run.md).

**Mitigation source expérimentale, sans adoption :** la seconde copie `/tmp/forgejo-merge011-fix-test/source`, toujours au commit `ea9ae1e…`, lit le SHA de branche dans la transaction de contrôle, vérifie les refs réellement fetchés, recalcule la divergence au lieu de se fier au cache, puis protège l’écriture avec `--force-with-lease`. Trois fenêtres déterministes montrent refus avant fetch sur divergences et refus au push après déplacement post-fetch. Le groupe des chemins merge/rebase/squash/FF/AutoMerge passe avant l’ajout d’une dernière assertion; le test post-fetch actuel et `services/pull` passent séparément. Cela montre une option serveur plausible, pas une décision d’adoption : LFS peut être envoyé avant le lease, et AutoMerge peut perdre sa planification quand le CAS échoue. Le détail complet et les empreintes sont dans le [rapport MERGE-011](../evidence/merge-011-base-freshness-race-local-run.md). Aucun code de ce patch n’est présent dans le produit.

Forgejo est le registre du code et le système de collaboration Git. Le noyau agentique est un service/librairie Rust unique et modulaire — pas une flotte de microservices. Les premiers adaptateurs parlent à Forgejo par API et à l’agent par un contrat versionné. Les secrets de fusion et la clé du vérificateur ne sont jamais montés dans le workspace de l’agent.

### Liaison persistante issue→exigence

Le champ `source_issue_number` du document d’exigences v2 est le lien versionné. Il est couvert par le hash exact des exigences, donc par l’identité de mission et le claim. L’admission v2 compare ce champ au numéro d’issue relu depuis Forgejo avant allocation et valide tous les documents canoniques `requirements/*.json` au même commit. Un second document v1/v2 mal formé ou v2 sans lien, une liste incomplète, une entrée non canonique ou un autre document lié au même numéro bloque l’allocation. La liste locale est plafonnée à 512 exigences et l’arbre Forgejo à 20 000 entrées et 256 pages; les dépassements échouent fermés. L’adaptateur local lit la taille configurée de page, calcule le nombre de pages depuis `total_count`, vérifie la taille exacte de chaque page et lit chaque blob au même SHA. Au commit Forgejo audité `ea9ae1e174ac290febcd92f57e7a28ccb58262d0`, l’implémentation conserve `truncated=true` sur la dernière page si l’arbre entier dépasse une page, contrairement au commentaire de l’API; l’adaptateur accepte les deux conventions, mais ne s’en sert pas pour décider de la fin. Le comportement et l’endpoint ont aussi été confrontés à l’instance locale 17.0.0+gitea-1.22.0. Le claim et le bail revérifient la cohérence du DTO, pas l’authenticité de sa provenance. Le chemin canonique est `admit_and_claim_mission_v2`; l’ancien chemin d’admission sans allocation durable a été retiré. Les méthodes publiques bas niveau du journal restent des API de l’hôte de confiance : elles acceptent des DTO constructibles par l’appelant et ne prouvent pas qu’ils viennent de l’adaptateur Forgejo. L’agent non fiable ne doit jamais recevoir ces méthodes, le journal ou l’autorité de l’hôte. L’adaptateur ne vérifie toujours ni la règle détaillée de protection ni l’approbation qui autorise la modification des exigences; ce chemin reste sandbox-only.

## Interfaces minimales

Chaque objet porte son propre numéro de schéma : l’interface runtime est v1, les exigences avec autorisation d’issue sont v2. La première interface utilisable est une CLI structurée (`capabilities`, `mission`, `context`, `verify`, `decision`, `merge`) avec JSON machine et erreurs comprenant `code`, `retryable`, `action` et `details`. Les commandes mutantes exigent une clé d’idempotence. Une API HTTP ou MCP ne sera ajoutée qu’après identification des clients et de l’interface réellement disponible dans AgentOS/Forge Code.

- `src/agent_runtime.rs` implémente les DTO Rust sérialisables `AgentExecutionRequestV1`/`AgentExecutionResultV1` et le trait `AgentRuntimeV1::execute(request, host_owned_tool_port)`. La requête transporte les octets exacts d’exigences v2 et leur hash SHA-256; la validation exige un `source_issue_number` positif, et les opérations de claim/bail vérifient qu’il correspond au numéro d’issue reçu. L’admission refuse les exigences v1 ou un lien absent/incohérent avant allocation. Les anciennes exigences v1 restent lisibles pour migration, mais ne sont plus admissibles. La requête lie aussi le contexte aux exigences et au commit de base, exige des plages de citation UTF-8 ordonnées qui couvrent tout le texte et réfèrent chaque source, vérifie les chemins autorisés, et lie le candidat au workspace, à la base et à l’ensemble des chemins d’écriture. Elle ne prouve pas que le fournisseur a obtenu chaque source du blob Git : ce dernier doit relire le commit et vérifier les hashes. Le résultat reste une référence de candidat, pas une preuve. Le contrat n’expose aucune capacité de vérification, secret Forgejo ou fusion; la persistance des clés d’idempotence et l’application des limites au niveau OS restent aux hôtes.
- `AgentExecutionResultV1` a reçu `idempotency_key` sans changer le numéro de schéma. `serde(default)` laisse les anciens JSON v1 se désérialiser, mais la validation refuse leur valeur vide. Aucun consommateur externe n’a été constaté; avant de publier ou partager cette interface, incrémenter le schéma ou préparer une migration coordonnée et testée. Cette évolution n’est pas rétrocompatible au niveau du contrat.
- `tests/agent_runtime_contract.rs` contient le seul adaptateur exécutable de ce lot : un fixture déterministe sans modèle qui lit le document d’exigences et le texte de contexte, écrit un programme Rust, le compile et exécute le binaire. Son port de test refuse les outils et chemins hors liste et compte les appels. Il n’est pas un adaptateur de production : il n’isole pas le processus, ne peut pas interrompre sûrement une commande après `timeout_ms`, ne persiste pas les répétitions entre redémarrages et ne mesure pas de tokens réels. Aucun runtime AgentOS/Hermes n’est prétendu.
- `ToolCallReceiptV1` lie hashes d’entrée/sortie, durée, succès et code d’erreur. Le port fixture enregistre également les appels refusés et les dépassements de budget, sans stocker les sorties brutes dans le reçu. Ce reçu atteste l’appel du port; il ne démontre ni la sûreté ni la correction du résultat.
- `ContextProviderV1.build(repo, commit, requirement_revision, token_budget) -> ContextManifest`: cite chemins et lignes, hash du commit, fraîcheur, provenance et budget. Il inspecte le dépôt vivant et n’emploie un index RAG que comme accélérateur reconstructible.
- `VerifierV1.verify(candidate, base, requirement_hash, policy_hash) -> ProofOutcome`: charge la politique depuis une révision protégée, vérifie les artefacts et exécute les tests dans un environnement séparé, sans accès aux secrets de fusion. Résultat fermé parmi `pass`, `fail`, `inconclusive`; preuve absente ou environnement indisponible = `inconclusive`.
- `MergeGateV1.merge(pr, proof_id)`: interface planifiée, pas encore câblée à un merge live. Elle devra prendre un verrou de base, relire exigences/politique/base/tête/revues/preuve et garder le verrou du read-back final jusqu’au POST de merge et au read-back terminal. Le préflight CLI actuel retourne sans autoriser ni tenter une fusion; son `BaseBranchMergeLock` ne protège pas le POST ultérieur. `head_commit_id` lie la tête mais ne conditionne pas la base côté Forgejo. Le pilote API est acceptable seulement avec un écrivain de merge unique et des permissions contrôlées; sinon le serveur doit vérifier une base attendue sur la voie de merge.
- `ForgejoAdapterV1`: lecture des issues/PR/commits/protections/statuts et ouverture/fusion de PR. `WebhookInboxV1` valide HMAC-SHA-256 sur le corps brut, déduplique un même UUID de livraison et conserve les événements dans une inbox append-only. Le récepteur local borne quatre workers, seize requêtes normales et un rejector avec une seule place de file; il lit une requête excédentaire complète avant de répondre 503. Au-delà de cette borne, les sockets excédentaires sont fermées. Ce chemin est mesuré dans [WEBHOOK-020](../../../evidence/webhook-020-local-run.md). Sur Unix, SIGINT/SIGTERM arrête l’acceptation, draine les files puis joint les workers; un test local a vérifié la relecture dédupliquée après redémarrage. Forgejo v17.0.0 ne réessaie pas automatiquement les réponses non-2xx, donc le 503 ne suffit pas à assurer la livraison. Forgejo attribue un UUID neuf à une relecture manuelle; `reconcile_inbox_events` conserve chaque résultat de livraison mais regroupe les lectures API par ressource dans un lot borné. `ForgejoCurrentState` relit une issue ou une PR dans l’API et valide l’identité de la réponse, y compris l’URL HTML exacte dérivée de la configuration canonique de l’adaptateur; l’état et les liens du payload ne font jamais autorité. Le seul client API livré est un adaptateur local de test allowlisté.

Un reçu de preuve lie au minimum : versions et hashes des exigences et de la politique; commit de tête candidat, base réellement testée et résultat de fusion; identité du vérificateur; environnement et version des outils; commandes; hashes des artefacts; date, résultat et signature. Tout changement de ce tuple impose un nouveau verdict. Le contrôle ne lit jamais un statut fourni par l’agent comme preuve.

## Identité des livraisons webhook

Le registre d’inbox conserve une ligne par UUID Forgejo : le même UUID et le même contenu sont idempotents, le même UUID avec un contenu différent est un conflit, et un UUID neuf représente une nouvelle tentative enregistrée. Sur Forgejo v17.0.0, `ReplayHookTask` copie le payload mais produit un UUID neuf; le test local confirme donc deux reçus pour deux livraisons du même contenu. Le corps seul ne sert pas de preuve d’identité métier, puisqu’un contenu identique ne démontre pas qu’il s’agit de la même occurrence.

La réconciliation ne transforme pas les reçus en état concurrent : elle relit la ressource par API et regroupe les lectures d’un lot. L’identité de mission dérive de l’issue et du hash d’exigences; l’UUID de livraison est exclu. Les transitions d’allocation, de claim et de lease utilisent `EventJournal::transact_mission` : elles prennent un `flock` stable par mission puis tentent sans attente le verrou global pendant la lecture/décision/append. Une contention à l’un ou l’autre niveau retourne `execution_mission_busy` et `retryable=true`; la transition ne conserve donc pas le verrou mission en attendant une transaction générique. Une closure `EventJournal::transact` ne doit pas rappeler une opération bloquante sur le même journal. `with_valid_lease` tient le verrou mission, relit les événements via une tentative non bloquante, valide le bail, puis relâche le verrou global avant l’effet hôte court; webhook et autres missions progressent. L’horloge est fournie par fermeture et échantillonnée après l’acquisition des verrous, puis contrôlée à nouveau avant l’effet. `append` et `transact` génériques refusent les trois types d’événement réservés; chaque transition valide les records mission du journal avant d’agir. Le répertoire des locks est privé, ses fichiers restent stables et ne doivent pas être supprimés pendant l’usage; journaux et locks à liens physiques multiples sont refusés pour conserver une identité de verrou unique. Cette coordination ne vaut qu’entre processus coopératifs utilisant le même chemin canonique sur un système de fichiers compatible avec `flock`; les hashes d’exigences différents donnent des missions différentes et exigent des workspaces distincts. Le verrou ne sandboxe aucun processus et ne protège pas les références Git ou ressources partagées hors du contrat hôte. Le fixture n’isole pas le candidat ou son réseau; le CLI n’acquiert pas de lease et aucun effet Forgejo n’est effectué. Voir [MISSION-005](../../../evidence/mission-lease-001-local-run.md) et [MISSION-006](../../../evidence/mission-lock-001-local-run.md).

`admit_reconciled_issue_v2` prend `JournaledWebhookEventV1`, que seule la relecture du journal peut construire, et un binding v2 fourni par l’hôte. `append` et `transact` génériques refusent les types webhook réservés; l’ingestion les écrit après validation HMAC. Le raccord vérifie le type, le dépôt, le numéro et l’URL canonique configurée de l’adaptateur avant tout appel API, puis réconcilie l’issue ouverte. L’admission relit l’issue, la branche protégée et les octets d’exigence au commit exact, compare le SHA-256 épinglé par l’hôte avant l’allocation et le claim. Le delivery ID reste une provenance et n’entre pas dans l’identité/allocation. Aucun enregistrement d’autorisation d’admission n’est persisté et le scope ainsi que l’empreinte attendue restent des entrées hôte. Le HMAC est vérifié à l’ingestion mais non stocké ni revalidé à la relecture; le journal local n’est pas protégé contre un écrivain du même UID. Aucun CLI de déclenchement ni admission Forgejo live positive n’est démontré; les dix contrats utilisent des ports fixtures. [WEBHOOK-MISSION-001](../../../evidence/webhook-mission-admission-001-local-run.md).

## Sauvegarde du journal et rétention

L’append appelle `sync_all()`, et une copie cohérente à un instant peut prendre le même verrou latéral `flock` que le journal. Cela ne rend pas la copie fraîche après sa prise : le test WEBHOOK-013 montre qu’un POST peut attendre le verrou, être acquitté 202 après le snapshot, puis disparaître si l’ancienne copie est restaurée. Le consommateur actuel relit l’état canonique Forgejo; un futur déclenchement métier sur chaque webhook n’aurait pas cette protection.

Le JSONL n’est pas encore un mécanisme de sauvegarde/restore produit. Avant tout usage durable, définir RPO, quiescence ou replay après restore et validation de la chaîne; ne pas supprimer d’anciennes lignes avant de spécifier compaction et conservation des clés de déduplication. Les [scénarios de restauration WEBHOOK-012/013](../../../evidence/webhook-013-local-run.md) sont des fixtures locales, non des garanties d’exploitation.

## Verrou de fusion local — MERGE-001

`src/forgejo.rs` fournit `BaseBranchScope` et `BaseBranchMergeLock`. La portée comprend origine, propriétaire, dépôt et branche; le nom du fichier est dérivé d’un SHA-256 avec champs préfixés par leur longueur. Le répertoire dédié doit appartenir à l’utilisateur effectif et être en mode `0700`; le fichier régulier doit être en mode `0600`. Les liens symboliques sont refusés. `flock` exclusif non bloquant est repris jusqu’au délai, puis retourne `TimedOut`. Garder le verrou vivant du dernier préflight à la relecture post-merge; ne pas supprimer les fichiers tant qu’un processus peut les rouvrir.

Ce verrou ne sérialise que les processus qui l’utilisent sur le même hôte et système de fichiers local. Il n’empêche ni un appel API direct, ni un administrateur, ni un autre hôte ou un service contournant le verrou d’avancer la base. MERGE-001 ne connecte pas encore le verrou à un endpoint de fusion et n’a fait aucune écriture Forgejo. Les six tests de contrat couvrent l’attente interprocessus, la séparation de branches, les portées invalides et les liens symboliques; la preuve détaillée est [MERGE-001](../../../evidence/merge-001-local-run.md).

## Préflight en lecture seule — MERGE-002

`forgejo-reconcile-local --preflight` réutilise le client local borné et non authentifié. Sous le verrou de base, il fait un GET à la PR, lie la réponse au numéro demandé, à l’origine canonique, à l’URL et aux dépôts head/base, puis compare tête et base courantes à une `ExpectedBinding` fournie par l’hôte et vérifie la preuve HMAC passante. Une tête/base différente est refusée. Les verdicts conservent trois états : `Outcome::Fail` produit `rejected/proof_failed`, `Outcome::Inconclusive` produit `inconclusive/proof_inconclusive`, et preuve absente/périmée reste `inconclusive`.

`proof_current` signifie uniquement que la preuve correspond au snapshot lu. Le préflight ne lit pas les revues humaines et n’autorise ni n’appelle l’endpoint de merge; la source de l’ExpectedBinding et la clé doivent rester sous le contrôle de l’hôte. Un essai réel, sans écriture, sur la PR locale #18 a lu une seule fois l’API puis refusé une vieille preuve avec `stale_base`; l’état relu est resté ouvert/non fusionné. Voir [MERGE-002](../../../evidence/merge-002-local-run.md). Cette lecture reste un snapshot et ne résout pas la course face aux écrivains Forgejo non coopératifs.

## MERGE-004 — autorité de fusion

La relecture du commit Forgejo `ea9ae1e174ac290febcd92f57e7a28ccb58262d0` confirme que `head_commit_id` protège le candidat lors du POST, mais que l’API n’accepte pas une précondition de base testée. `force_merge` peut permettre à un administrateur de contourner les protections; le client devra donc toujours omettre/refuser ce champ et utiliser une identité non-administratrice. L’API de revue relie une approbation au head, mais l’audit du code montre que le retarget d’une PR et l’avance de sa base ne rendent pas systématiquement les approbations périmées. Une approbation au head ne suffit donc pas à prouver qu’elle a été donnée pour la base testée. La lecture REST des règles de branches est admin-only, donc les règles de déploiement doivent venir de la politique au commit protégé et être imposées par Forgejo. Voir [l’audit MERGE-004/009](../evidence/merge-004-source-audit.md).

Le pilote garde le verrou par branche seulement si un seul gate/compte non-admin peut fusionner, les pushes directs sont bloqués et les autres merges passent par le même verrou. Le SHA de base est relu avant le POST et vérifié après fusion; cette barrière ne résiste pas à un administrateur de l’instance ou à un writer qui contourne le gate. Si cette limite ne convient pas au déploiement, ajouter une précondition de base au point de fusion dans un fork limité, avec son coût continu, plutôt que de prétendre que le verrou local est atomique. L’API live n’était pas consultable sans authentification au lot MERGE-004; aucun contrôle de revue réelle ni merge n’est revendiqué.

Le contrat local `validate_merge_approvals` accepte seulement un snapshot complet lié à l’origine/dépôt/PR attendus, une politique dont les octets correspondent au hash attendu et une approbation officielle au SHA exact par un ID de reviewer autorisé distinct de l’exécutant. `stale` et `dismissed` doivent être présents. Il ne lit pas Forgejo, ne prouve pas que les octets viennent d’un commit protégé, ne prouve pas que le reviewer est humain et n’autorise pas la fusion. Sans `merge_approval_policy`, il échoue fermé. Les 18 tests ciblés sont des fixtures; les pages ne constituent pas un instantané atomique et aucun adaptateur HTTP ni credential hôte n’est raccordé. Détails et journaux : [MERGE-004](../evidence/merge-004-source-audit.md).

MERGE-008 ajoute `evaluate_merge_readiness`, qui compose le preflight signé avec l’approbation d’un snapshot complet pour le même dépôt/PR, la base et la tête courantes. La décision éphémère expose les hashes d’exigences/politique, le vérificateur, le commit de base et le candidat, l’empreinte du snapshot de revues et les reviewers acceptés. La politique déclarant le vérificateur est comparée à l’identité du proof; une divergence échoue avec `VerifierMismatch`.

MERGE-009 ajoute un contrat d’attestation hôte par `review_id`, `base_branch` et `base_commit`. La readiness refuse une attestation absente, d’une autre PR, dupliquée ou qui ne correspond pas à la base courante; la décision expose la branche de base et l’empreinte canonique des attestations. Le test rouge reproduit qu’en omettant cette validation une revue sans attestation produit encore `Ok`. Cependant, Forgejo ne fournit pas cette liaison dans l’API de revue. Le fixture Rust qui alimente les tests synthétise les bindings et ne démontre ni leur provenance ni une intégration. Au commit audité, `ChangeTargetBranch` écrit la nouvelle base puis crée séparément l’événement de timeline; une erreur entre les deux peut laisser la base changée sans événement. Les mises à jour de base recalculent la divergence sans invalider les revues; l’invalidation observée se fait au changement de diff de la tête. Il faut donc garder l’autorité de merge bloquée jusqu’à l’existence d’une source réellement fiable de la base examinée lors de chaque approbation et d’une relecture/contrôle final au point de fusion. Aucun appelant de production, lecteur authentifié, adaptateur de cette attestation ou POST n’existe. Voir [le rapport MERGE-009](../evidence/merge-009-base-binding-local-run.md) et les références Forgejo dans [l’audit source](../evidence/merge-004-source-audit.md).

MERGE-010 rend `pull_request_url` obligatoire dans le DTO et compare chaque URL de revue à la PR de la portée attendue, lors de la collecte et de l’évaluation directe. Le générateur respecte le préfixe configuré et l’encodage Go `net/url.PathEscape` utilisé par Forgejo; un mismatch ou champ absent échoue fermé. Le fingerprint des revues passe au schéma canonique v2 pour inclure cette valeur. Ce contrôle empêche qu’un DTO d’une autre PR soit accepté sous le scope courant, mais n’authentifie pas le transport ni la réponse. La source fiable de la base d’approbation reste absente; aucune autorité de merge n’est accordée. [Rapport MERGE-010](../evidence/merge-010-review-url-local-run.md).

## Menace et frontières

**Actifs :** branche protégée, critères, secrets, preuves et disponibilité du vérificateur. **Entrées hostiles :** code et workflows de PR, issues, documents indexés, payloads webhook et sorties d’outils. **Acteurs séparés :** exécutant non fiable, vérificateur sans autorité de fusion, merge gate et administrateur humain/Forgejo.

- Dans le déploiement visé, le compte exécutant n’a pas de droit d’écriture sur `main`, la politique ou les statuts du dépôt de base; il pousse sur son fork et ouvre une PR. Il ne peut pas appeler l’API de fusion. Les règles de base exigent PR/revue et s’appliquent aux administrateurs. Cette isolation de comptes n’est pas encore appliquée par le prototype : aucune frontière de processus/service ne sépare l’agent du journal et de l’adaptateur de confiance.
- Un `success` arbitraire, une preuve manquante, une preuve rejouée, un hash périmé ou une branche de base avancée ne donne jamais `pass`. Les refus sont inspectables.
- `BaseBranchMergeLock` est une coordination locale volontaire, pas une frontière de privilège ou une primitive atomique Forgejo. Un administrateur ou un autre écrivain ne la respecte pas nécessairement; pour un modèle multi-hôte ou hostile, il faut imposer l’autorité unique côté service avant d’autoriser une fusion.
- Le récepteur local `src/webhook.rs` et `src/webhook/http.rs` traite les doublons, conflits et événements désordonnés par inbox durable et clé d’idempotence. L’ingress n’a pas de dépôt configuré dans son interface : toute livraison authentifiée et structurellement valide est conservée dans l’inbox partagée; le scope owner/repository est imposé plus tard par le réconciliateur cible. Un événement Release étranger reste donc journalisé, mais `forgejo-reconcile-local` le rend `resource_out_of_scope` avant le moindre GET ou lecture du credential hôte; [CONTINUATION-414](../evidence/continuation-414-foreign-release-scope-001/local-run.md) vérifie cette frontière au processus. Le routage automatique vers un autre adaptateur n’est pas implémenté. L’inbox est bornée à 64 MiB cumulés; le receiver, la réconciliation et l’admission refusent sans rotation automatique une inbox plus grande ou un append qui dépasserait le quota. La capacité et la politique sont visibles dans `--capabilities`. Un HTTP 507 n’est pas réessayé automatiquement par Forgejo v17.0.0; après sauvegarde et migration/compaction vérifiée (non fournie), l’opérateur doit redélivrer manuellement. `src/webhook/reconcile.rs` transforme un événement vérifié en référence issue/PR, puis relit l’API et refuse une réponse indisponible, incohérente ou incomplète; aucun état n’est écrit dans une seconde base. Pour une PR, l’instantané inclut maintenant le SHA courant de la tête et de la branche de base; un SHA manquant/invalide rend l’état non canonique. Cette lecture permet de détecter une base avancée, pas de rendre la fusion atomique.
- `src/bin/forgejo-reconcile-local.rs` est un adaptateur de démonstration, pas un client de production : configuration JSON v1 limitée à `http://127.0.0.1:3130` et `forge-admin/agent-forge-core`, champs inconnus refusés, aucun jeton ni en-tête d’authentification. L’appelant peut fournir `--config <fichier>`; sans option, les mêmes valeurs locales fixes s’appliquent. L’environnement de sous-processus est vidé, `curl` ne suit pas les redirections et les délais/réponses sont bornés. L’exécutable s’est néanmoins connecté depuis le compte local sans isolement egress; les réponses loopback anonymes peuvent être usurpées par un autre processus local et ne sont pas une source d’autorité. Cette limite est conservée dans les preuves.
- L’exécution du candidat n’a ni secret, ni socket Docker, ni réseau sortant. La séparation par worktree seule n’est pas une frontière de privilège. Le premier bac à sable utilise Bubblewrap avec mounts limités, politique read-only, namespace réseau sans accès et délai/ressources bornés. Si ces propriétés ne sont pas démontrées sur l’hôte, le parcours ne lance pas de code candidat.
- **Limites résiduelles :** l’administrateur OS peut contourner l’outil; une vulnérabilité du noyau, de Bubblewrap ou du compilateur reste possible; une suite de tests peut être incomplète; le sandbox local n’est pas une preuve de résistance universelle. Aucune certification n’est revendiquée.

Forgejo lui-même signale que les commandes `host` du runner sont exécutées sous l’identité du runner sans isolation (source officielle : [sécurité Actions](https://forgejo.org/docs/v15.0/admin/actions/security/)). Docker étant installé sans daemon sur cet hôte, aucun runner Forgejo Actions ne sera démarré. La vérification isolée est un processus local distinct; une preuve signée enregistre sa provenance mais pas, à elle seule, la correction.

### MERGE-015 — profil de cible typé du gate de fusion local

`--merge-local-test` accepte un préfixe optionnel `--target-profile <sélecteur>` avant le numéro de PR. Les cibles sont un enum compilé, `LocalForgejoTargetProfile`. Chaque variante est un tuple littéral indivisible (origine, propriétaire, dépôt), et la branche de base reste `main` :

| Sélecteur | Origine | Dépôt | Défaut |
|---|---|---|---|
| `merge-014-agent-forge-core` | `http://127.0.0.1:3130` | `forge-admin/agent-forge-core` | oui (aucune sélection) |
| `mission-012-clamp` | `http://127.0.0.1:3132` | `forge-admin/mission-012-clamp` | non |

Garanties de construction :
- Aucune origine, aucun hôte, aucun port ni aucun dépôt ne provient d’argv, d’un fichier ou de l’environnement.
- La correspondance du sélecteur est exacte et sensible à la casse. Un sélecteur inconnu, vide, non UTF-8, un `--target-profile=…`, une autre option `--…` ou une sélection répétée sont refusés avant le numéro de PR, la lecture du FD de credential, la lecture des fichiers d’entrée et tout appel réseau.
- Le constructeur de production `merge_api_for_profile` lie la portée de l’API et l’origine du credential au même profil. La plomberie du credential (pipe anonyme hérité, lié à l’origine, jamais dans argv, l’environnement ou les fichiers) est inchangée.
- Toute la décision dérive de `api.config` : portée du verrou, snapshot de PR, revues, protection, identités de reviewer, fraîcheur de `main`, relecture finale, POST de fusion, readback de PR, du commit de fusion, de `main` et de l’issue.
- `request_api_once`, seul chemin HTTP, n’accepte que trois formes de route : `/user`, `/users/<login>` et `/repos/<propriétaire>/<dépôt>/…` du dépôt configuré. Toute autre route, y compris `/repositories/{id}`, est refusée avant toute connexion, comme les segments vides, `.` ou `..` et tout `%` avant la query.
- Le wrapper refuse aussi un credential lié à une autre origine que celle de l’API.
- `curl` garde `--proto =http`, `--noproxy '*'` et ne suit pas les redirections.
- Le résultat JSON porte `target` : sélecteur, origine, propriétaire, dépôt et base. Le wrapper refuse une API dont le dépôt ne correspond pas au profil.

Portée volontairement étroite :
- La réconciliation webhook (`--config`) et `--preflight` restent limitées à la cible par défaut.
- Dans `--capabilities`, `configuration.allowed_origins` reste `[3130]`, avec `allowed_origins_scope=["reconcile_webhook_deliveries"]`, puisque seul `--config` lit ce fichier, et `selects_merge_target_profile=false`.
- Le préflight déclare `target=fixed_default_profile` et `reads_configuration_file=false`.
- Le profil 3132 n’apparaît que dans `local_test_merge_authority.target_profiles`, avec `uses_configuration_allowed_origins=false`.

Frontière de schéma avec MISSION-012 : la politique MISSION-012 v4 (`policy/MISSION-012-CLAMP-001-v4.json`, SHA-256 `e23907b5bd6b2c0f342c88ddcfa9f9a9be98065adcd24f9f7299dc796b5739eb`) n’est pas un document `Policy` du gate.
- `Policy` refuse les champs inconnus et exige `verifier_id`, `environment`, `acceptance_command`, `commands`, `protected_criteria`, `timeout_seconds` et, pour fusionner, `merge_approval_policy`.
- La v4 porte à la place `id`, `verifier_identity`, `agent_capabilities`, `candidate_policy`, `verification`, `merge_policy` et `limits`. Le gate la refuse après le verrou et avant toute lecture Forgejo.
- Le rapport de `mission-012-verify-local` n’est pas une `SignedProof`.
- Le gate ne lit aucun statut de commit, donc `required_status` de la v4 n’est pas appliqué.
- MERGE-015 n’intègre donc pas la politique historique v4. Pour viser 3132, l’hôte doit fournir une politique au schéma du gate, une `ExpectedBinding`, une `SignedProof` et un binding de revue propres à ce dépôt.

Limites supplémentaires :
- La preuve signée, `ExpectedBinding` et le binding de revue ne contiennent ni origine ni dépôt. Ils sont liés aux SHA de commits, aux hash d’exigence et de politique, au vérificateur et au numéro de PR. Un jeu produit pour une cible reste donc acceptable pour l’autre si les mêmes PR, base et tête y existent. Revues, protection, whitelist et acteur de fusion restent relus en direct sur la cible choisie.
- Lier la portée dans la preuve changerait le contrat signé existant ; ce n’est pas fait. `--capabilities` l’expose : `proof_binding_scope=commit_and_policy_hashes_not_target_bound`.
- Les profils ne sont donc pas isolés l’un de l’autre au niveau de la preuve.
- Aucune instance Forgejo n’a été démarrée et aucune fusion réelle n’a été tentée pour ce lot.

### MERGE-016 — preuve V2 liée à la cible

La fusion locale exige maintenant un `TargetBoundProofV2` strictement versionné. Son MAC HMAC-SHA-256, avec séparateur de domaine `agent-forge/target-bound-proof/v2`, couvre la cible canonique complète (profil, origine, propriétaire, dépôt, branche de base) et l’évidence. L’autorité reconstruit la cible depuis le profil compilé et `api.config`, compare d’abord cette cible à celle du reçu, puis vérifie le MAC et les bindings courants avant son premier GET Forgejo. V1 conserve son type et sa vérification; le préflight V1 reste consultatif, tandis que l’autorité de fusion refuse V1 avant tout appel réseau et ne le convertit pas en V2.

La politique locale exige une clé V2 d’au moins 32 octets au signataire et au vérificateur. Une clé plus courte produit `invalid_verifier_key` avec une action et `minimum_bytes=32`, avant toute requête Forgejo. Ce minimum contrôle la longueur, pas l’entropie ni la qualité de génération de la clé. La lecture privée impose toujours fichier régulier, propriétaire UID courant et mode 0600, mais ne crée aucune séparation de privilèges : un agent ayant le même UID ou lisant la clé peut signer son propre reçu. Le MAC atteste l’intégrité et la provenance par possession de clé, pas la correction du code, l’identité du processus ni l’isolement de l’environnement.

Les tests refusent les cibles différentes, un changement de chacun des cinq champs lorsque la même cible modifiée est aussi attendue, une clé vide ou de 31 octets, les reçus malformés et V1 avant toute requête. Ils tournent contre une API loopback de fixture dans la copie de validation, sans instance Forgejo réelle ni modèle LLM. Le contrat n’établit donc pas encore le parcours fusionné avec un agent réel ou une frontière de privilèges vérificateur/exécutant. Voir [les journaux et fixtures MERGE-016](../evidence/merge-016/README.md).

### Contrat de réconciliation des publications

La source officielle Forgejo v17.0.0 auditée est épinglée au commit `0d791421f85ca13a63b665053d81ea765fbbc571`; aucun de son code n’est copié. Les symboles examinés sont `modules/structs/hook.go::{HookReleaseAction,ReleasePayload}`, `modules/structs/release.go::Release` et `routers/api/v1/repo/release.go::GetRelease`. L’événement natif `release` accepte `published`, `updated` et `deleted`, puis le client effectue un GET canonique repository-scoped `GET /api/v1/repos/{owner}/{repository}/releases/{release_id}`. La projection expose uniquement `id`, `tag_name`, `draft` et `prerelease`; les notes, assets et URL reçue du webhook/API ne sont pas propagés. L’URL de page est dérivée du tag courant et de l’origine configurée de confiance. La réponse v17 n’a pas de `updated_at`; la sortie le laisse donc nul. Un 404 reste `inconclusive`, car une publication absente peut aussi signaler une ressource ou un dépôt inaccessible.

Le read route est une entrée GET exacte de l’allowlist `ReconciliationReadOnly`; les identifiants nuls, non canoniques, les sous-routes, autres dépôts, query/fragment et méthodes mutantes restent refusés avant requête. La découverte publie le contrat webhook v9 tout en conservant v8; les sorties CLI courantes sont single 19, batch 23 et capacités 28 (`forgejo-reconcile-capabilities-v28`). Les testeurs et consommateurs doivent valider la version annoncée.

Le support n’ajoute ni RAG, ni moteur mémoire, ni orchestrateur, ni dépendance. Il ne prétend pas qu’AgentOS est installé; le parcours LLM et le benchmark restent non démontrés.
