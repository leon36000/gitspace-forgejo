# POC-061 — couverture réelle du préconditionnel de ref et récupération LFS

Date : 25 octobre 2026. Source scratch `/tmp/forgejo-v17-base-cas-poc`, Forgejo officiel v17.0.0, commit de base `0d791421f85ca13a63b665053d81ea765fbbc571`. Le checkout est détaché et largement modifié par les POC précédents; cette tranche a ajouté des sorties d'essai et un test d'intégration de renommage, sans modifier de code produit ni copier du code Forgejo dans le produit. Détails d'empreinte : [source-hashes.txt](source-hashes.txt). Versions : [tool-versions.txt](tool-versions.txt).

## Observations vérifiées

1. **Contrôle d'écriture Git et merge de PR** — `TestGitPushExpectedBaseCommitIDRequired` et `TestPullMergeExpectedBaseCommitID` passent ensemble (2/2). Le hook `preReceiveBranch` refuse un `ExpectedBaseCommitID` périmé ou l'absence d'un contexte PR serveur; le merge normal sous la politique configurée réussit avec le SHA attendu.
2. **API de fichiers + LFS en refus** — `TestExpectedBasePolicyRejectsFileAPIAndLeavesLFSMetadata` passe. L'API reçoit 403; la branche reste sur son SHA, aucune association LFS active n'existe et le GET LFS renvoie 404, mais une association pending est conservée. Elle n'expose pas le contenu au lecteur LFS dans ce cas, mais laisse un résidu.
3. **Promotion après interruption** — `TestPOCGenericFileLFSRecoversAfterPostReceiveInterruption` passe. Après le commit/ref et une omission simulée de la promotion post-receive, un appel direct à `RecoverLFSPendingMetaObjects` promeut l'association et le GET LFS renvoie 200. C'est une reprise manuelle par le test, pas une récupération automatique.
4. **Écritures directes hors receive-pack** — `TestPOCExpectedBasePolicyDoesNotGateAPIBranchDelete` passe : après avance du ref et activation de la politique, `DELETE /api/v1/repos/.../branches/...` reçoit 204 avec un `expected_base_commit_id` périmé dans la requête et supprime le ref. Le test ajouté `TestPOCExpectedBasePolicyCanBeBypassedByAPIBranchRename` passe aussi : le `PATCH` de renommage du ref par défaut répond 204 sous la même politique et préserve son commit courant; cette route ne reçoit aucun token de base, car le schéma de requête de renommage n'en expose pas.

Dans les tests d'intégration concernés, l'activation du réglage est faite directement sur l'unité de configuration du dépôt par le test. Ce run ne vérifie ni sa surface utilisateur/API, ni sa migration, ni le comportement d'une configuration déjà existante.

Ensemble des sorties et commandes : [tests fichiers/LFS](integration-tests.log), [push Git et merge PR](writer-route-control-tests.log), [renommage direct](api-branch-rename-bypass.log), [suppression directe](api-branch-delete-bypass-existing.log). Une première forme du harnais de renommage a retourné `no tests to run`; cette sortie est conservée dans [initial-no-test-selection.log](initial-no-test-selection.log) et ne compte pas comme vérification. Le test a ensuite été recentré sur le seul `onApplicationRun` et exécuté effectivement 1/1.

## Lecture du code et limites

`assertExpectedBaseCommitID` est appelé depuis `preReceiveBranch`; ce point couvre les mises à jour qui traversent le hook Git. Les routes API de suppression et de renommage aboutissent aux helpers `services/repository/branch.go::DeleteBranch`/`RenameBranch`, qui modifient les refs via les helpers Git locaux au lieu de receive-pack. Le champ de politique est donc **non universel** sur les writers/routes. Ce POC ne passe pas en revue exhaustive de chaque écrivain de ref (miroirs, migrations, packages, wikis, tags, autres flux internes restent à cartographier).

Une recherche de call sites, sans exécution des handlers UI, trouve aussi `routers/web/repo/branch.go` pour la suppression de branche, `routers/web/repo/pull.go` pour l'action de suppression après merge, et `routers/web/repo/setting/protected_branch.go` pour le renommage. Ces routes partagent les helpers directs `DeleteBranch`/`RenameBranch`; le résultat est donc un signal de couverture supplémentaire, pas trois tests comportementaux. La création API et UI délègue à `CreateNewBranchFromCommit`, qui appelle `git.Push` vers le dépôt local; son interaction avec la politique stricte reste à établir par test et n'est pas classée comme bypass ou réussite.

Les lignes LFS pending sont utiles à la reprise après un commit accepté, mais la recherche du scratch trouve les fonctions de récupération dans leurs définitions et les tests; aucun worker/appelant de production n'est raccordé. Pour un ref refusé, la récupération actuelle diffère la ligne non atteignable et ne la supprime pas. Une simple suppression après lecture de reachability ne serait pas atomique avec un push concurrent. La course de snapshot observée en POC-060 demeure aussi ouverte.

Les tests démarrent l'application Forgejo de test avec SQLite, stockages locaux sous `tests/integration/forgejo-integration-sqlite/` et HTTP/SSH loopback. Ce n'est ni un serveur installé, ni Forgejo production. Aucun test PostgreSQL/MySQL, réseau externe, LLM, secret ou modèle n'est exécuté. Le checkout scratch accumule 19 fichiers source modifiés (`git diff --stat`: 1 405 insertions, 85 suppressions) et de nombreux tests/rapports non suivis; ces chiffres caractérisent tout le laboratoire LFS/CAS, pas le coût attribuable à ce seul préconditionnel.

Les journaux d'intégration montrent `FATAL ERROR: log.Error has been called` pour certains refus attendus ou erreurs de nettoyage avec contexte annulé, alors que les assertions du test et le processus terminent `PASS`. Ces lignes sont du bruit du logger de tests, pas un résultat d'échec; elles sont conservées pour transparence et ne sont pas interprétées comme un verdict fonctionnel.

## Décision et suite

Ne pas adopter ce patch de précondition comme une politique de serveur universelle, ni porter du code Forgejo au produit. Forgejo reste un socle plausible par interfaces; le POC ne montre pas que son noyau doit être fusionné. Avant toute adoption d'une politique CAS, dresser et tester la matrice de tous les writers/ref routes et décider quels clients transmettent leur version attendue ou sont explicitement refusés. Pour LFS, décider du cycle durable stage → commit/ref → promotion → reprise → rétention/nettoyage; raccorder un worker uniquement après les tests d'interruption/concurrence et une politique de GC fondée sur des références partageables.

Pas de correction de ces bypasses dans cette tranche; l'objectif était d'établir le périmètre par code et test. Le parcours LLM et le benchmark comparatif demeurent non démontrés.
