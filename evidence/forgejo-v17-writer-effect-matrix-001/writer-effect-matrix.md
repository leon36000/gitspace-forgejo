# Forgejo v17 — matrice des effets des writers et des refs

Date : 25 octobre 2026. Référence officielle examinée : Forgejo `v17.0.0`, commit `0d791421f85ca13a63b665053d81ea765fbbc571`. L’arbre `/tmp/forgejo-v17-base-cas-poc` est un laboratoire séparé, fortement modifié par des POC; au relevé, il contient 58 entrées de statut Git, dont 19 fichiers Go suivis modifiés. Les conclusions de code ci-dessous s’appuient sur les objets `HEAD` officiels, sauf lorsqu’il est explicitement question du patch scratch. Aucun code Forgejo n’est copié ni adopté dans le produit.

## Méthode et couverture

Le scan lexical complémentaire de POC-075 cherche des appels `push`, `update-ref`, `SetReference`, `RemoveReference`, `DeleteBranch`, `RenameBranch` et les marqueurs de précondition. Il retourne 35 chemins, identiques à ceux du scan POC-075; liste exacte dans `writer-scan-paths.txt`, comparaison dans `previous-scan-compare.txt`, appels repérés dans `write-call-sites.txt`, et classification chemin par chemin dans `writer-classification.tsv`. Les 35 chemins sont classés ci-dessous par effet. Ce nombre est **un nombre de fichiers candidats**, pas un nombre de writers. Le scan omet des registres de routes et des chemins indirects; par exemple `routers/api/v1/api.go` enregistre les endpoints de branche et de tag mais ne figure pas dans les 35. Les handlers de tag, les plugins/hooks externes, tous les scripts d’administration et un graphe d’appels complet n’ont pas été audités. La matrice n’est donc pas exhaustive.

La distinction de preuve est importante : les symboles dans `HEAD` décrivent le code amont propre; les résultats de POC-052/061/062/063/070/075 ont été obtenus dans le scratch contenant le hook CAS expérimental et ne sont pas des tests du binaire amont intact. Aucun test ni compilation n’a été exécuté pour cette tranche statique. Les commandes et versions figurent dans `commands.txt`, `scratch-state.txt` et `source-hashes.txt`; `upstream-source-blobs.txt` fixe les objets Git officiels lus.

## Ce qui est démontré sur l’autorité et la compatibilité

Le code amont montre des familles d’écritures différentes : receive-pack, helpers Git directs, writers internes, refs PR, dépôt temporaire, wiki, fork et remote miroir. Une précondition installée uniquement dans `pre-receive` n’est pas une barrière globale. POC-052/061/070 ont démontré, avec le hook expérimental, que l’API DELETE branche et les routes Web/API de renommage/suppression peuvent muter une branche sans passer par ce hook; les routes de création traversent le hook mais ne fournissent pas la base attendue. WRITER-RESTORE-POLICY-071 complète ce lot : la restauration web passe par le hook, mais la création sur une ref absente échoue avec la politique stricte et l’UI masque la cause derrière un flash générique. Les expériences de promotion LFS numérotées POC-071/073 appartiennent à une série différente et restent référencées sous leurs noms complets dans le checkpoint. POC-002 a aussi testé que l’API et le formulaire de merge acceptent l’appel legacy lorsque le champ de base est omis; les chemins AutoMerge et `manually-merged` ont le même problème de contrat. POC-075 a trouvé une course entre le readback post-receive et les mises à jour SQL PR/LFS dans le patch scratch.

Les routes de branche API partagent un contrôle `reqRepoWriter(unit.TypeCode)`; le code observé ne donne pas une permission distincte « fusionner cette PR, sans pouvoir appeler les autres writers ». MERGE-020 a déjà exercé un mergeur non-admin et un lecteur de politique séparé, mais n’a pas tenté les mutations directes de branche avec le même credential du mergeur sous la protection configurée. Le `403` du lecteur de politique à DELETE ne prouve pas cette séparation : son rôle Forgejo est `admin` et c’est un scope token limité. Les gardes additionnelles de protection de branche peuvent isoler certaines actions; leur effet sur chaque route et le push direct doit être vérifié avec l’identité exacte du mergeur avant de compter sur une autorité unique.

L’ajout d’une métadonnée `ExpectedBaseCommitID` à un push ne crée pas non plus un fence partagé. `RenameBranch`, `DeleteBranch`, `SetReference` et `RemoveReference` sont des chemins directs; le flux merge touche Git, l’état PR SQL et les associations LFS SQL; un check ref puis un commit DB laisse une course entre les deux. Le scratch a des essais d’ACK récupérable (POC-071/073) et de récupération, mais aucune transaction atomique commune Git/DB, aucun worker de production, aucun déploiement distribué ni test PostgreSQL/cluster. Un stage LFS ne devient pas publié seulement parce qu’un hash est signé.

## Évaluation d’intégration

1. **Interfaces autour de Forgejo amont** : choix par défaut pour les issues, PR, webhooks, statuts et données de dépôt; faible coût de rebase car aucun patch du noyau. Pour les merges à preuve obligatoire, l’adaptateur seul n’est pas une autorité de mutation : il faut démontrer un acteur unique effectivement isolé et relire l’état au moment du merge. Cette isolation est encore ouverte.
2. **Fork limité** : pas adopté. La couverture identifiée traverse routes API/Web, services de refs, hooks, merge/rebase et stockage LFS/SQL. Le scratch entier présente 19 Go suivis modifiés, mais ce nombre inclut de nombreux POC; il ne mesure ni un patch minimal ni un coût de maintenance upstream. Aucun coût en heures n’est défendable. Un changement de noyau ne sera évalué qu’après preuve qu’une API d’autorité unique/ACL Forgejo ne suffit pas et qu’un protocole partagé peut être testé.
3. **Fusion profonde** : aucun besoin établi. Les interfaces Forgejo couvrent déjà les objets et opérations de collaboration; les changements d’exécution/preuve restent une couche séparée. Elle augmenterait la surface de synchronisation du noyau sans résoudre seule la cohérence Git/SQL/LFS.

Décision actuelle : conserver Forgejo comme forge Git et surface PR, et garder la couche agentique indépendante; ne pas adopter le patch CAS/LFS du scratch. Cette décision d’intégration n’accorde pas encore au wrapper le rôle d’autorité sûre de fusion. Avant une fusion contrôlée qui prétend résister aux writers concurrents, tester les ACL avec identités séparées; à défaut, une petite interface d’autorité au serveur ou une contribution amont devra être spécifiée et évaluée comme chantier distinct.

## Prochaine action et limites

1. Tester sur l’instance d’intégration scratch si un acteur ayant le droit de merger une PR peut être privé en même temps des mutations API/Web de branche, des pushes directs et des chemins d’administration; utiliser des comptes non-admin et une branche protégée, et lire les refs après chaque refus. Inclure le contrat AutoMerge/manually-merged.
2. Si l’isolement par permissions échoue, concevoir un seul endpoint/service de merge qui exige l’identité de la preuve, le candidat et le SHA de base, puis recense quels writers doivent être refusés. Ne pas commencer par étendre encore un hook seul.
3. Pour LFS, établir le protocole stage → tentative de publication → ref confirmée → promotion/ACK → reprise idempotente, avec un fence qui couvre les mutations directes; le nettoyage doit rester refusé tant qu’il ne partage pas cette autorité. POC-068 démontre qu’un discard après simple observation d’absence peut effacer une métadonnée d’un candidat publié concurrent.

Pas de test/benchmark Forgejo lancé dans ce lot de consolidation de sources; WRITER-RESTORE-POLICY-071 est une preuve antérieure séparée, non relancée. Les POC antérieurs sont SQLite, seam locale et scratch modifié; aucun parcours LLM, déploiement, PostgreSQL/cluster, coût upstream précis ou gain comparatif n’est démontré. Le choix de licence produit demeure inchangé : aucune licence choisie, droits de redistribution non évalués.
