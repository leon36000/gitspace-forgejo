# Refus d'une sélection CLI répétant la même livraison — 25 octobre 2026

## Résultat

Le CLI Rust de réconciliation acceptait une liste contenant deux fois le même delivery ID, résolvait deux fois la même ligne d'inbox, puis pouvait consommer le credential hôte avant d'émettre deux résultats liés à la même livraison. Aucun caller ne devrait compter deux fois un résultat de preuve et le wrapper Python avait déjà une garde d'unicité; la garde manquait au vrai chemin CLI.

Le test unitaire `duplicate_delivery_selection_is_refused_before_host_credential_read` échoue d'abord comme prévu avec un FD invalide : la sélection dupliquée atteint le lecteur du credential avant de produire l'erreur de FD. Un second test-first traverse ensuite le vrai processus CLI et échoue encore plus directement quand la garde est temporairement retirée : le processus consomme le credential synthétique pour cette sélection invalide. Le correctif contrôle maintenant l'unicité avant toute ouverture/relecture de l'inbox et avant la lecture du credential. Il renvoie un lot schema 5 `inconclusive`, `duplicate_delivery_selection`, `retryable=false`, avec une action de correction et `requested_delivery_count=2`. Le test unitaire confirme zéro lecture upstream selon le compteur applicatif; le test processus confirme que le credential reste entièrement non consommé et que le journal ne change pas.

La règle ne confond pas une répétition du sélecteur avec deux nouvelles livraisons du même événement. Le test existant `batch_cache_budget_is_enforced_across_signed_journal_and_loopback_http` passe : des delivery IDs distincts liés à la même ressource demeurent valides et partagent leur lecture en cache.
