# MERGE-019 — relecture finale de la protection de branche

Date : 23 octobre 2026. Périmètre : gate local `forgejo-reconcile-local`, son fixture HTTP loopback, rapport et checkpoint. HEAD parent inchangé : `f3e2bb3a9f9b0cb3dbcd1e03f658f0b6a05119a0`. Aucun service Forgejo ni dépôt de production n’a été modifié.

## Constat et changement

Le gate chargeait `branch_protections` avant de vérifier l’acteur, les revues, le binding de revue, et la base. Son dernier contrôle HTTP relisait la PR et `main`, puis envoyait le POST. Une règle de fusion pouvait donc changer après sa première lecture et avant le POST.

Le gate conserve désormais le règlement `main` validé, relit `/branch_protections` dans la fenêtre finale après la PR et la base et avant l’unique POST, puis compare la règle structurée entière. Une règle manquante, ambiguë ou différente refuse avec `branch_protection_changed_during_gate`; une erreur HTTP ou une réponse HTTP 200 avec une forme JSON invalide est `inconclusive/upstream_invalid_response`. Deux tests process-like passent par le gate et le client HTTP : l’un change `merge_whitelist_usernames` entre les lectures, l’autre renvoie un objet JSON au lieu d’un tableau; les deux observent l’absence de POST.

Le test rouge pré-correctif a effectivement fusionné dans le fixture et échoué sur `assert!(!merge_authorized)`, démontrant que l’ancienne séquence ne relisait pas la politique; sortie conservée dans [red.log](red.log). La revue indépendante a relevé une classification trop affirmative pour un corps HTTP 200 mal formé; un test rouge a confirmé `rejected` avant la correction et il retourne désormais `inconclusive`, avec sa sortie dans [invalid-shape-red.log](invalid-shape-red.log). Les six tests focalisés `local_merge_gate` passent; [focused.log](focused.log). Le test positif des profils valide également le nouvel ordre GET de règle après le dernier GET de base et avant le POST.

## Portée, limites et reprise

La relecture finale ne rend pas atomique la politique au moment du POST. Le run live confirme que le gate détecte une mutation synchronisée avant son dernier readback; un administrateur peut encore changer la règle après ce GET, et un writer externe peut déplacer `main` après son GET, car l’API publique de merge ne prend pas de précondition `expected_base`. `flock` n’ordonne que les gate coopératifs sur le même hôte. L’exclusivité des writers, une identité gate à moindre privilège et la résistance à un administrateur restent non démontrées.

Au contrôle sûr de 23:40:02 −04:00, le processus Claude existant était vivant (CLI 2.1.310), mais le marqueur Ralph indiquait encore `active=true`, itération 1/6, mtime 21:00:03. Aucun prompt, argv, environnement, log ou transcript n’a été consulté; aucun processus n’a été relancé. Aucune nouvelle invocation payante n’a été lancée. Le heartbeat de reprise existant reste le mécanisme de continuation.

Suite : établir si l’exploitation peut garantir un writer de merge non-admin unique, vérifier les permissions réelles et les chemins de contournement; si un writer non coopératif reste dans le modèle, reprendre l’option CAS serveur et en chiffrer le coût upstream. Ne pas présenter un writer unique comme démontré avant vérification des droits et voies d’accès de l’instance.
