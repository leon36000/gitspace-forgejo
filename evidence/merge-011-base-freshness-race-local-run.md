# MERGE-011 — avance concurrente de `main` après la vérification

Date : 23 octobre 2026. Portée : caractérisation locale de Forgejo v17.0.0; aucun changement au code Forgejo, à une instance de production ou à l’autorité de merge du produit.

## Résultat observé

Le harnais réutilise le parcours PR local existant. Après le read-back prémerge et un `read_only_merge_preflight` (`proof_current`, `merge_attempted=false`, `merge_authorized=false`), il fait avancer `main` par une seconde PR approuvée par l’identité de fixture `forge-reviewer`. La PR cible reçoit ensuite un POST `/merge` avec son `head_commit_id` vérifié. Quand Forgejo a rafraîchi sa mergeabilité, le harnais relit une PR cible encore ouverte et refuse le retry avec HTTP 405 et le motif `The head branch is behind the base branch`. Le SHA de `main` reste celui du merge concurrent; `src/lib.rs` demeure absent de `main` (404), tandis que le marqueur README de la seconde PR est présent.

Quatre scénarios Forgejo indépendants, avec des dépôts et bases initiaux neufs, satisfont la classification fail-closed finale. Les runs 009–011 ont été réévalués hors ligne par le classifieur final après renforcement des assertions; le run 012 a exécuté de bout en bout la version finale du harnais :

## Reproduction déterministe de la fenêtre interne sur la source Forgejo

Pour fermer cette lacune, un test d’intégration instrumenté a été exécuté sur le commit officiel `ea9ae1e174ac290febcd92f57e7a28ccb58262d0`, dans la copie jetable `/tmp/forgejo-merge011-test/source`. Le clone d’audit officiel `/tmp/forgejo-audit-merge006` est resté propre. La copie jetable contient seulement un seam de test dans `routers/api/v1/repo/pull.go` et `tests/integration/pull_merge_freshness_race_test.go`; aucun changement Forgejo n’a été copié dans le produit ni commité.

`TestPullMergeBaseFreshnessTOCTOU` configure `block_on_outdated_branch=true`, désactive les pushes directs, exige une approbation, et applique la règle aux administrateurs. Il approuve une PR cible et une PR concurrente. Le seam API retient la cible après le succès de `CheckPullMergeable` et juste avant `pull_service.Merge`. La PR concurrente avance ensuite le ref Git `main`; le seam `TestSeamPostReceiveSync` déjà présent dans Forgejo retient sa synchronisation DB juste avant `SyncBranchesToDB`. Pendant cette pause, le test confirme que Git et DB ont des SHAs différents et que la cible avait été contrôlée avec `commits_behind=0`, puis libère la requête cible. Le test vérifie les réponses et read-backs des deux PR, les fichiers réellement présents sur `main`, l’ascendance du merge concurrent et l’égalité finale Git/DB. Son oracle n’accepte comme refus sûr que HTTP 405 avec le motif exact de branche en retard, PR cible toujours ouverte et fichier cible absent; il classe les états ambigus comme inconclusifs. Une revue indépendante a corrigé la barrière pour n’agir qu’une fois et a vérifié les reprises, joins et délais.

Les deux répétitions corrigées donnent le même résultat : la cible répond HTTP 200 et est réellement fusionnée pendant que la base Git a avancé mais que la DB indique encore l’ancienne base. La PR concurrente répond HTTP 200 et est aussi fusionnée. Les deux fichiers sont sur `main`; le commit de fusion concurrent observé pendant la pause est l’ancêtre du commit cible final, et le SHA final de Git égale le SHA DB. Le test finit donc en échec intentionnel à `TOCTOU OBSERVED` : c’est le verdict rouge qui confirme la course sur cette source, pas un échec de build ou d’infrastructure.

Portée précise : le commit final cible contient bien le commit concurrent dans son ascendance; ce test ne montre pas une perte de son changement. Il montre que la décision `block_on_outdated_branch` peut être prise sur un `CommitsBehind` périmé et laisser passer la fusion. Le test source n’y joint aucune preuve externe : il ne démontre pas à lui seul qu’une preuve attachée à l’ancienne base a été acceptée. Il établit néanmoins qu’un client ne peut pas déduire la fraîcheur de la décision de protection depuis le seul succès du POST; une preuve liée à la base doit être revérifiée ou liée côté serveur au SHA réellement fusionné.

## Expérience de mitigation source, dans une deuxième copie jetable

Une seconde copie du même dépôt officiel, `/tmp/forgejo-merge011-fix-test/source`, a servi à tester une mitigation sans toucher au clone d’audit ni au produit. HEAD reste `ea9ae1e174ac290febcd92f57e7a28ccb58262d0`, sans commit; le dépôt Forgejo déclare GPL-3.0 dans `LICENSE`. Le diff complet, test non suivi inclus, est archivé sous `/tmp/forgejo-merge011-fix-test/merge-011-expected-base.patch` (66 144 octets, SHA-256 `fa4a6ac37c50fc1a60cd7a7cc98ea9c7fb71cf1d611e79c635585643ca81c6e6`); le test E2E final a SHA-256 `672d19da7d2adff125817e092c7702fa1df784c3bccef1523aaffd134c5e24e3`. `gofmt -d` sur les 13 fichiers et `git diff --check` réussissent.

La copie prend `git_branch.CommitID` dans la transaction du contrôle de merge et le transmet aux chemins API, Web et AutoMerge. À la préparation, elle compare ce SHA à la base réellement fetchée. Si le ref a changé, elle refuse; si le SHA de la branche et Git sont déjà synchronisés mais `CommitsBehind` est encore périmé, elle recalcule le retard sur les refs Git fetchés lorsque `block_on_outdated_branch` s’applique. Le résultat préparé doit descendre du SHA vérifié; le push final utilise `--force-with-lease` sur le ref de base attendu. Le refus de branche en retard ressort en HTTP 405; un ref déplacé après le fetch ressort en HTTP 409 `merge push out of date`. La correction de fixture AutoMerge resynchronise aussi le modèle `git_branch` après un reset Git de test.

Le rouge initial sur la copie non corrigée observe le merge cible accepté après le précontrôle. Sur le patch, trois tests déterministes séparent les fenêtres : (1) Git base avancée alors que la DB est encore ancienne, (2) refs Git et DB à jour mais cache `CommitsBehind` ancien, (3) base concurrente avancée après fetch et avant le push CAS. Les premiers deux refusent la cible en HTTP 405; le troisième échoue le push en HTTP 409. Les trois vérifient que la cible reste ouverte/non fusionnée, son fichier est absent, le fichier concurrent est présent et le SHA de base final concorde entre Git et DB. Le scénario post-fetch vérifie aussi le SHA de base capturé lors du contrôle. Il passe seul après cette dernière assertion.

Le run d’intégration sélectionné passe en `71.913s` sur la version du test immédiatement antérieure à cette dernière assertion : les trois fenêtres de fraîcheur, merge, rebase, rebase-merge, squash, fast-forward divergent/non divergent et les huit variantes de `TestPullAutoMergeAfterCommitStatusSucceed`; log `/tmp/forgejo-merge011-fix-test/green-final-merge-paths-and-races.log`, exit 0, SHA-256 `23022071ed13f7b6b74ed47cecb198a81382dfd0844ef093db11f115d366319a`. Après l’assertion finale, `TestPullMergeBaseFreshnessAfterFetch` passe seul, exit 0, log `/tmp/forgejo-merge011-fix-test/green-final-after-precheck-assertion.log`, SHA-256 `9bf08b5966c2cbe942eb35586edf2c48dc7fe4d84311b5e8069ae78225807182`. Le paquet `./services/pull` passe aussi, exit 0, log `service-pull-package-final.log`, SHA-256 `826d3cda7a42a5bca2c820d6c1dc488f0301d333ed6bb501506d5e5b412ecc44`. Il n’y a pas de run groupé final après l’assertion; ces deux niveaux sont rapportés séparément.

Le test final isolé journalise des `TestLogger FATAL ERROR` de teardown malgré `go test` exit 0. Les messages de logger AutoMerge ont aussi été reproduits sur le baseline non patché; aucun n’est reclassé comme succès silencieux. Le premier run groupé avait échoué parce qu’un helper réinitialisait le ref Git sans resynchroniser la row DB; cet échec est conservé, puis le fixture corrigé passe dans le run groupé sélectionné.

**Cette expérience ne constitue pas un correctif produit ou amont.** Le clone officiel d’audit est resté propre et aucun fichier Forgejo n’est entré dans le worktree produit. La suite complète Forgejo n’a pas été exécutée; le groupe sélectionné n’exerce pas toutes les voies UI/AutoMerge sous une course. `LFSPush` précède le push CAS et peut téléverser des objets non référencés avant un refus; cela n’a pas été testé. Le chemin AutoMerge supprime sa planification avant `Merge`; une erreur CAS réelle peut donc perdre la planification sans requeue. Le comptage et le nettoyage d’objets LFS, notifs/index/cache, autres writers, autres hôtes et stockage non SQLite restent hors couverture. Un verrou applicatif ne remplace pas le lease Git ni une précondition atomique couvrant les writers externes.

## Couverture, limites et suite

Le point d’injection se situe après les dernières lectures du driver, juste avant son premier POST de merge cible. Après l’avance de base, le premier POST a répondu « Please try again later » pendant le rafraîchissement asynchrone; le harness a attendu un read-back `mergeable=true`, puis le retry a été refusé explicitement. Cela démontre le comportement de `block_on_outdated_branch` **après propagation du nouvel état** dans ces quatre courses locales. Le run 008 est conservé comme diagnostic mais exclu du décompte `n=4` : le serveur a renvoyé le même motif dans la forme enveloppée `not allowed to merge [reason: …]`; le classifieur intermédiaire, trop strict, l’a marqué non classifié et a échoué fermé. Les tests et les répétitions 009–011 couvrent cette forme réelle.

Le test E2E du binaire v17 décrit plus haut injecte encore le mouvement avant le POST. Le test source instrumenté, lui, place les deux barrières dans l’intervalle serveur et confirme l’acceptation d’une cible périmée quand le recalcul DB est retenu. Cela ne prouve pas que le binaire v17 local provient du commit source testé; aucun comportement n’a été observé sur une instance déployée. Le test ne couvre pas non plus un autre administrateur, `force_merge`, toutes les courses de pagination des revues, ni un attaquant de même UID. Les identités sont des fixtures locales; aucun modèle, AgentOS, RAG ou CI conventionnelle n’a été utilisé dans ce sous-test.

La CLI Rust actuelle tient `BaseBranchMergeLock` seulement pour le préflight en lecture seule; la copie Forgejo ci-dessus teste un mécanisme serveur, pas un gate produit. Suite utile : un gate hôte Rust qui relit PR/base/revues/politique sous verrou et garde celui-ci jusqu’au POST/readback, puis un parcours PR dont le driver ne fusionne plus directement. Le verrou local coordonne seulement les callers coopérants; il n’empêche pas un writer Forgejo externe. Une précondition atomique serveur reste la protection nécessaire contre ces writers. Comparer le coût de maintenance upstream avant tout patch Forgejo de produit.

Les sources et les vérifications locales du harnais sont couvertes par `merge-011-base-freshness-race-sha256.txt`. Les états d’instances de test restent dans `/tmp` pour permettre leur inspection locale; aucune suppression n’a été faite.
