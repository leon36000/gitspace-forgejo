Le run vert n’est pas extrapolé depuis les anciens snapshots.

## Parcours et résultat observés

Le runner courant démarre une instance jetable Forgejo `17.0.0+gitea-1.22.0` au commit de source Forgejo `0d791421f85ca13a63b665053d81ea765fbbc571`; SHA-256 du binaire `e5ec437cd6357e8d1b4580cb47ab1daa58a32b33971a63db63446a535d33adb7`; commit de construction du binaire inconnu. Les contrôles hôte réussissent : health/API dépôt/Web dépôt HTTP 200. Les trois cibles de sonde sont l’API de PR #1 et la page Web de cette PR (toutes deux 404 parce que la fixture n’a pas de PR), puis `git-receive-pack` anonyme (401).

Le processus réel `mission_012_test_agent_adapter.py --stdio-mcp` est lancé sous Bubblewrap avec `--unshare-net --unshare-pid`. L’adaptateur essaie `socket.create_connection()` puis `sendall()` pour chacune des sondes API, Web et receive-pack vers le port Forgejo 3130; une `OSError` ajoute la route à `direct_forgejo_routes_blocked`. Le reçu courant indique les trois routes bloquées, `network_connected=false`, un namespace réseau distinct, les seuls FD `[0,1,2]` et `credential_visible=false`. Le compteur `supervisor_observed_route_connections=0` désigne les connexions inattendues reçues par le listener MCP éphémère du gate; ce n’est pas une observation des sockets Forgejo. Les contrôles positifs de l’hôte confirment que Forgejo est actif pendant le run.

Limite de mesure importante : la sonde enfant ne lit pas de réponse HTTP et ne conserve pas le type/errno de l’exception pour chaque route. Le reçu établit les erreurs de connexion/envoi rapportées par le processus isolé, pas des statuts HTTP enfant ni la phase exacte de l’échec. Le listener MCP du gate ne surveille que son port éphémère; il ne mesure pas les connexions au port Forgejo. Les statuts API/Web PR `404` et receive-pack `401` consignés sont les contrôles exécutés depuis l’hôte; les routes PR n’existent pas dans cette fixture.

La barrière est placée sur `mission_context` après l’acceptation corrigée. Le parent observe l’enfant vivant avant et après, avec PID/start-time et namespaces stables. Pendant cette attente, le gate de confiance lit `main` par `GET /api/v1/repos/forge-admin/mission-012-clamp/branches/main` (HTTP 200); le SHA avant, pendant et après est identique. L’enfant n’obtient pas le credential local à portée `write:repository` : il reste en mémoire dans le parent et un memfd `CLOEXEC`, n’est ni écrit dans un fichier ni sérialisé dans la commande/configuration/environnement, aucun FD n’est hérité, et la sonde `/proc/<pid-hôte>/fd/<fd>` échoue dans le namespace PID enfant. Aucun `POST /merge` n’a été appelé.

Le processus adaptateur lit le contexte via MCP, exécute le vrai `cargo test --offline --locked` sur le dépôt fixture : l’exigence échoue d’abord (`exit 101`, `left: -2`, `right: 10`), puis le changement MCP corrige le code et le test passe (`exit 0`). Le reçu dit `source_changed_through_mcp=true`. Forgejo s’arrête avec code 0 et le listener 3130 est absent. Résultat détaillé : `result.json`; source et toolchain exacte : `provenance.json` et `source/`; sorties de test : `acceptance-baseline.log` et `acceptance-corrected.log`.

## Portée et limites

Ceci est une frontière de processus et réseau observée sur cet hôte, dans ce scénario précis. L’agent est le `local-test-adapter` déterministe, pas un LLM ni AgentOS; le MCP host est une fixture locale allowlistée. Le parent de confiance effectue un GET read-only pendant que le child est vivant. Le jeton a `write:repository`, mais cette instance ne contient aucune PR et aucun appel merge n’est fait : le reçu prouve l’absence de transfert d’un credential à portée d’écriture, pas qu’un token donné aurait été autorisé à fusionner une PR. L’hôte et Forgejo partagent l’UID local; cela ne démontre ni isolation multi-tenant, ni résistance à un noyau compromis/évasion, ni l’absence universelle d’egress. Le test n’enregistre pas les errno par route; une prochaine amélioration instrumentale peut les conserver si une distinction connect/send est nécessaire. Les tests précédents ne sont pas remplacés; ils ont leurs propres snapshots.

La mission reste incomplète : aucun AgentOS/LLM ni benchmark comparatif contrôlé n’est démontré ici, le parcours PR→vérification indépendante→merge reste à lier à cette frontière, et les licences/droits de redistribution demeurent non résolus.
